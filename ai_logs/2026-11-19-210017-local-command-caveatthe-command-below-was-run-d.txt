  3. The duplicate rule when running incrementally

  The problem. An incremental run rebuilds only recent date partitions. If we
  partition by answer date, one sitting can sit in two partitions: started
  23:50, finished 00:20. Or a pupil leaves a sitting and comes back days later.
  Rebuilding only the newer partition then goes wrong in two ways:
  - Copies of a duplicate could fall on both sides of the boundary and get
    counted twice. This doesn't happen today, because copies share a timestamp,
    but nothing guarantees it.
  - A sitting that started on an old day and completes now has early answers in
    a partition we don't rebuild, so those answers never get counted.

  My advice: partition by the sitting's finish date, not the answer date. Define
  sitting_date = date(finished_at, 'Europe/London'). That's the same UK day
  boundary you asked for, applied to the sitting.
  - A whole sitting then lives in one partition, so duplicates are always
    deduplicated together. The plan guarantees this; it doesn't depend on luck
    in the data.
  - A sitting only counts once it's complete. When it completes, its finish date
    is recent, so the next run picks it up with no extra logic.
  - It's more correct point-in-time. A sitting that finished after as_of_date
    was incomplete on that date, so it shouldn't count. The mart filters on
    sitting_date <= as_of_date. Using today's is_complete alone would let it in.
    I'd keep the answered_date <= as_of_date filter too, for the 1-second-late
    answer that crosses midnight.
  - To read responses, the incremental run takes sittings with sitting_date
    inside the window. It then reads responses from one day before the window
    start, which catches the part of a sitting before midnight.

  The other options, and why I wouldn't pick them:
  - Keep partitioning by answer date and widen the rebuild to every partition a
    touched sitting covers. This works, but the window changes each run and is
    hard to explain.
  - Use the merge strategy keyed on session_id + question_id. CLAUDE.md asks for
    insert_overwrite, and a merge at 100M+ rows costs more.

  Decision C: partition by sitting_date (finish date)? This changes the README
  layout row ("partitioned by answer date"). It also needs finished_date added
  to stg_assessment_sittings. That's a cast, so it's allowed in staging, and it
  keeps one definition of the day boundary.

  What I'm unsure of: reading responses from one day before the window assumes
  no sitting runs past one midnight. I haven't checked how long sittings last.
  Before we build, I'd run one read-only query for the longest sitting, then add
  a data test that fails if any sitting spans more than one UK date.

  4. Partition and cluster columns

  Both models use the same settings:
  - Partition: sitting_date, daily. The mart reads a date range (1 September to
    as_of_date), so BigQuery skips every partition outside it. Daily also
    matches the lookback, which is counted in days. Ten years is about 3,650
    partitions, under BigQuery's limit of 4,000.
  - Cluster: pupil_id, subject_name. These are the columns the mart groups and
    joins on. This is your CLAUDE.md rule, and it suits these queries.

  Decision D: keep the column name subject_name to match staging and the seed?
  CLAUDE.md says "subject". The English → Reading mapping happens in the mart,
  so I'd keep subject_name here.

  5. Lookback window: I agree with 3 days

  - With partitions by finish date, the lookback only has to cover late-arriving
    rows: answers or sittings that land in raw after their date. It doesn't
    also have to cover how long sittings last, which it would with answer-date
    partitions.
  - 3 days covers a pipeline outage over a weekend. Each run rewrites only 3 or
    4 daily partitions, which is cheap.
  - The window is counted back from the latest sitting_date already in the
    target table, never from current_date(), so runs stay reproducible.
  - What I'm unsure of: raw has no load timestamp, so we can't measure the real
    delay. 3 is a judgement. In production you'd set it from the measured delay.
  - The limit: a sitting deleted or corrected more than 3 days after it finished
    won't be picked up. The fix is a scheduled --full-refresh, for example
    weekly. I'd note that in the README, not build anything for it.

  The intermediate models never read as_of_date. They hold everything, and only
  the mart applies the point in time. This keeps a re-run for any past date
  exact.

> Before the mart: our incremental models use the default on_schema_change,
  which silently drops new columns. Give me the trade-off between fail and
  append_new_columns, and your advice. Make the change once I decide.

● In plain words: both settings stop the silent drop. They differ in what
  happens to rows already in the table.

  fail: the run stops with an error whenever the model's columns no longer match
  the table. You then run --full-refresh on purpose, and every row is rebuilt
  with the new column filled in.
  - Pro: a column is never half-filled. Every row comes from the same logic, so
    a re-run gives the same output, as CLAUDE.md asks.
  - Pro: it also catches a column that was removed or renamed.
    append_new_columns ignores those.
  - Con: every schema change needs a full rebuild. At 100M+ rows that costs real
    money and time, but schema changes are rare and planned.

  append_new_columns: dbt adds the new column to the table and carries on.
  - Pro: there's no full rebuild, and the pipeline keeps running.
  - Con: only the partitions in the lookback window get real values. Every older
    partition holds NULL in the new column.
  - That's a problem here, because every row feeds a score. Take our own

  Plan: fct_pupil_subject_sats_score

  What it is

  One row per pupil, subject and as_of_date. Each run builds one as_of_date and
  replaces only that date's partition, so earlier dates are kept.

  How a row is built

  1. Rows to fill. Every non-deleted pupil (242) × every subject in the seed (2)
     = 484 rows per as_of_date. Pupils with no evidence still get their row.
  2. The as_of_date.
     - If the as_of_date variable is set, use it.
     - If not, use max(sitting_date) from the daily totals. That's never
       current_date().
  3. Evidence window. From 1 September of the academic year that contains
     as_of_date, up to and including as_of_date, filtered on sitting_date. A
     date in September or later uses 1 September of the same year; earlier dates
     use the year before.
  4. Year group reset. Keep only the rows for the pupil's latest year_group
     inside the window.
  5. Sums. Add up n_questions, n_correct and n_not_attempted. Then pct_correct =
     n_correct / n_questions, as NUMERIC.
  6. Converting to the KS2 scale.
     - Equivalent raw mark = pct_correct × max_raw_score. That's 50 for Reading
       and 110 for Maths.
     - Look up the two whole marks either side in the seed and interpolate
       linearly between their scaled scores.
  7. Flags.
     - below_scale: the equivalent mark is under 3, the lowest mark GOV.UK gives
       a scaled score. The score is set to 80.
     - low_evidence: n_questions is under 20.
  8. score_status. scored when there's evidence in the window, otherwise
     no_answers_in_window.
